## 目标、范围与边界

- **Goal：** 修复已确认的构造失败清理缺口；形成兼容的 provider 所有权方案；提高当前状态、远端测试、最低 Go 版本验证及文档的可维护性。最终交付与实际证据一致，不宣称未经验证的发布就绪。
- **Scope：** 当前运行时的定点加固及回归测试、相关契约与文档、既有测试/CI/证据机制的必要改进、少量高频公开 API 示例、可审阅的发布准备材料。
- **Out of scope：** 大规模重组目录、改变公开导入路径、扩充管理 API、引入通用框架、无依据升级依赖、生产操作、真实业务数据、部署或发布。
- **Likely changes：** `config.go`、`client.go` 及定向测试；经契约确认后可能涉及 `auth`、`internal/authn`；`scripts`、`tests/remote`、CI、证据检查；既有文档和验收记录。是否修改每个文件以实际调查为准。
- **Risks：** 擦除调用方或 provider 仍持有的秘密；改变公开生命周期、错误和重试语义；远端清理越界；最低版本和证据检查脱节；覆盖用户已有修改。
- **Validation：** 使用项目当前规定的命令和证据格式；定向回归先行，按影响扩大到必要检查；结果绑定实际候选工作树与工具链，记录真实退出码和实际执行目标。
- **Stopping condition：** 授权范围内独立任务完成，适用检查和审查完成；无法准备的外部条件明确为 BLOCKED。用户暂停、未决业务契约或授权缺口只阻塞依赖项，不阻止其他工作。不得为了完成清单弱化门禁。

遵守实际生效的全局、项目和目录级 `AGENTS.md`。如规则要求独立角色，按角色边界安排：主代理负责源码、契约、测试和文档写入；子代理只承担授权范围内的定位、核对、验证或审查，遵守并发上限与禁止再次委派的要求。

## 第一轮：构造失败时清理 SDK 自有秘密

针对 `normalizeConfig` 与 `newClient` 的失败返回路径，先梳理每份敏感数据的来源、克隆位置、所有权转移点和清理责任。

- 建立能观察实际清理行为的定向回归：在 RoleID / TLS 私钥已克隆后发生配置校验错误，以及规范化成功后 Option / 传输 / 协议初始化失败。选择实现中确实可达的路径，不伪造失败位置。
- 统一清理仅由 SDK 在本次构造中新建、尚未交付的副本。成功构造后继续由正常生命周期负责。
- 验证原始调用方配置和共享值仍可使用；成功客户端不被提前擦除；重复或部分初始化清理安全。
- 遵循 `sensitive.Bytes` 的共享擦除句柄语义，不将结构体赋值误认为独立克隆，不承诺 Go 内存的绝对擦除。
- 不打印凭据、不使用真实秘密做堆转储，不通过新增公开接口暴露内部秘密来便利测试。

完成定向检查和必要独立审查后继续下一项，不将这处加固描述为已经证明发生的凭据泄漏。

## 第二轮：先确认 provider 所有权，再改清理逻辑

核对 `TokenSnapshot`、`SecretIDSnapshot`、内建 provider、认证管理器以及第三方自定义 provider 的既有兼容行为。建立 EXPECTED / IMPLEMENTED / CONSUMED / VERIFIED 对照。

- 明确返回快照是否允许复用或共享擦除句柄、由谁清理、何时失效，以及失败、取消、刷新和并发时的责任。
- 将没有既有批准依据的所有权变化标为 proposed；不能把测试或实现当成已批准的新合同。
- 在兼容方案尚未确定前，不对任意 provider 返回值直接调用 `Zero`。优先寻找不破坏现有第三方 provider 的方案；若必须改变公开承诺，先给出具体影响与可审阅方案，暂停依赖的实现。
- 对确认后的方案，覆盖内建独立快照、自定义共享句柄 provider、重复读取、失败/取消及并发。同步 GoDoc、生命周期说明和必要测试。
- 清楚记录 TLS 已解析私钥和 Go 运行时的内存存留边界，避免绝对安全承诺。

契约未决时继续下列独立工作，不编造用户决定。

## 第三轮：让当前状态与远端测试可复核

### 文档状态一致性

- 校对 README、兼容性、handoff、测试指南和证据索引的“当前”结论，修正同一源码基线下相互矛盾的描述。
- 明确区分补充 `sdk-test` PASS 与正式 `REAL_OPENBAO` 集成通过；保留集成、扫描和 release gate 的实际阻塞/失败。
- 在既有台账和证据模型上，建立小而清楚的当前摘要生成或一致性校验，减少手工重复维护。不删除历史失败，不将全部旧记录重写为成功，不随意归档或破坏消费者格式。

### 远端测试运行清单

- 调查 Python / Go 入口与测试中硬编码的一次性 run ID、资源前缀和历史摘要依赖，提取可复用的准备、执行、报告与清理逻辑。
- 将通用 harness 纳入版本管理前先脱敏；不要直接把 `.artifacts` 整个目录、凭据或历史运行原始数据搬入仓库。
- 设计不含凭据的 per-run manifest，明确目标 allowlist、namespace、run ID、资源前缀、所有权、预算、有效期、允许操作与清理范围；其摘要绑定输出报告。
- 保留有限请求计数、失败停止、过期拒绝、范围校验、证据绑定和仅清理本次自有资源等保护。不要用一个宽泛的“允许远端”开关取代这些限制。
- 本地验证非法目标/namespace、资源已有、重复和过期运行、预算耗尽、前缀越界、部分失败、清理失败；不合法计划须在网络前失败。
- 先交付可本地验证的代码和清单样例。真实远端执行需要本次明确的目标、namespace、有效期、请求/资源预算与清理授权。旧的 120 请求与时间窗口已经结束，不能自动续用。

## 第四轮：补齐兼容性与正式验证条件

### 最低版本

- 复核 `go.mod` 的 Go 1.25.0 承诺，以及主 CI 使用 Go 1.26.3 的现状。
- 增加独立的最低版本验证作业/证据类型，并同步 `scripts/evidence.py`、`scripts/ci-summary.py` 与必要测试。保留主工具链的原有严格验收，不能单纯放宽正则。
- 至少验证构建、公开 API 消费和必要测试；声明支持的 Linux/Windows 范围应对应实际执行记录。
- 工具链准备必须在既有授权内。环境不存在时交付作业和验证方案，记录 NOT_RUN/BLOCKED，不能暗中更改最低版本来消除问题。

### 正式集成与安全扫描

- 查清 `deploy/test/server-lock.json` 的未验证状态，准备准确版本和经过可信来源核验的二进制或 digest 固定镜像方案。
- 在现有授权允许的隔离非生产环境运行正式集成；安全扫描沿用固定版本工具与真实数据库来源。如果要支持离线执行，同步设计工具来源、版本、数据库和报告校验，保持门禁等价。
- 只有现有材料不能确定安装、联网、服务启停或远端操作的授权时，才提交具体目标、操作与风险说明，等待必要授权；等待期间继续独立的代码、文档和本地检查。
- 不把 mock、补充远端、HTTP 200、截图或空测试集当成正式集成成功；不通过改验收条目、降低覆盖标准、移除必验目标或改源码指纹制造 PASS。
- 保留首次失败、重跑、日志、真实退出码、执行目标、版本和当前源码标识；重新运行发布门禁并如实报告剩余拒绝。

## 第五轮：改善高频接入与发布准备

- 优先补齐 `New/Start/Close`、provider、敏感值、主要 KV/PKI/Transit API 的必要 GoDoc，解释生命周期、权限、所有权、错误及 `UNKNOWN` 的处理责任。
- 添加少量确定性、无网络的可执行 `Example`。可评估加密/解密、Rewrap/HMAC、SignCSR/Read/Revoke 的示例价值，但不为每个方法机械建文件，也不扩充无需求的 API。
- 远端示例必须显式配置和执行，不自动操作共享资源；不嵌入真实密钥、证书私钥或 token。
- 整理当前未发布变化、兼容性影响、已验证/未验证范围与恢复限制。安全报告联系方式和支持承诺须来自维护者，不编造。
- 保持现有包结构、公开导入路径、设计风格和依赖方向。已有性能基准、延迟采样和 observer 不重复建设；没有真实负载依据时，不添加异步队列、监控依赖或虚构性能门槛。

## 贯穿全程的验证与交付要求

1. 每轮先确认输入和契约，再做最小实现；修复优先建立能暴露问题的回归。对稳定候选执行必要验证和独立审查，修改后重查受影响结论。
2. 从现有项目命令选择定向检查，再按影响扩展 normal、consumer、fuzz、benchmark、tooling、integration、security 等。无需为简单文档变更机械重跑所有套件，但不能省略项目必需项。
3. 保护现有鉴权与租户边界、GET 列表协议、保守的 HMAC 密钥元数据处理、写操作结果不确定语义及敏感值所有权。不要添加无界查询、盲目重试或泄露原始响应。
4. 子任务使用 PASS / FAIL / BLOCKED / NOT_RUN，区分静态审查、模拟测试、真实服务与发布门禁。没有实际执行就不能写成通过；新增代码不能继承旧源码的测试结论。
5. 未经明确授权不安装依赖、不改共享环境、不操作生产，不 stage/commit/push/pull/merge/rebase/stash，不新建或切换分支，不创建标签或部署。不修改全局规则、模型、权限或审批配置。
6. 结束前检查 `git diff`、`git diff --stat`、暂存区和相关未跟踪文件，确认没有意外源码、生成文件、锁文件、秘密或大日志。保留用户原有变更。
7. 最终报告：完成事项与关键文件；契约决定及兼容影响；实际命令、源码基线与结果；审查发现及处理；剩余阻塞、解除条件和下一步最小动作。只把当前证据支持的范围称为完成，不把“实现完成”写成“可以发布”。
