## 优先处理的证据与兼容性缺口

### 正式集成与安全扫描尚未闭环

**事实。** [服务版本锁](../deploy/test/server-lock.json)仍为 `NOT_VERIFIED`，版本、镜像与二进制校验值未建立。当前 integration 报告为 `BLOCKED`，要求明确 `BAO_TEST_VERSION`，并提供经过验证的二进制或按 digest 固定的镜像。security 报告也为 `BLOCKED`，因为[扫描脚本](../scripts/security-test.py#L16)要求显式 `--allow-network`，尚未执行固定版本的扫描工具。

当前[发布回执](../.artifacts/runs/remote-retest-20260930-final/release-remote-retest-01.json)为 `FAIL`、退出码 1，有 25 项拒绝：正式集成、安全扫描、5 项 AC 和 18 项 OB 未满足。这里的 25 是门禁拒绝项数量，不代表发现了 25 个业务缺陷；同样，缺少扫描结果不代表已经发现或排除了依赖漏洞。

**建议。** 准备经过批准的非生产服务版本与来源校验信息，完成正式集成和固定版本扫描，将日志、退出码、实际运行目标与当前源码标识绑定。需要联网、安装、容器或服务操作时，先核对已有授权。若希望支持离线扫描，应设计明确的工具与漏洞数据库来源校验，不能仅去掉网络检查或伪造成功结果。[Go 官方漏洞检查说明](https://go.dev/doc/security/vuln/)和[漏洞数据库说明](https://go.dev/doc/security/vuln/database)可作为工具设计依据。

**验收。** 所需服务与工具来源可复核；真实检查完成且目标确实执行；失败和阻塞保留原始记录；缺失前置条件时门禁继续拒绝发布。

### 最低 Go 版本承诺缺少验证

**事实。** [go.mod](../go.mod#L3)声明 Go 1.25.0；[CI](../.github/workflows/ci.yaml)各 Go 作业使用 1.26.3；[证据检查](../scripts/evidence.py#L129)也只接受 1.26.3。已有主工具链测试不能直接证明最低支持版本可构建、可测试。[Go 官方文档](https://go.dev/doc/modules/gomod-ref)将 `go` 指令定义为模块所需的最低 Go 版本。

**建议。** 保留主工具链验证，并增加独立的最低 Go 版本作业与证据类型，至少覆盖构建、公开 API 消费和必要测试。同步[CI 汇总](../scripts/ci-summary.py)，不要只放宽现有证据校验的版本正则。若要调整最低版本，应作为公开兼容性决定单独说明。

**验收。** 明确区分最低版本与主工具链证据；本机未安装或未获准准备该工具链时记为 `BLOCKED`，不能以当前版本通过代替。Linux/Windows 的 CI 配置存在，也不等于当前工作树已经在两种系统实际运行。

## 运行时加固与契约事项

### 构造失败路径没有统一清理 SDK 新建的敏感副本

**已确认的静态发现。** [normalizeConfig](../config.go#L32)在认证与 TLS 配置处理中分别克隆 RoleID 和客户端私钥；之后仍可能因 `TLS.ServerName`、代理或超时配置不合法而返回错误。错误返回未对这些新副本调用清理。[newClient](../client.go#L41)在规范化成功后，遇到无效 Option、传输配置或协议客户端初始化失败时，也需要统一处理这些尚未交付的副本。

一个可用于后续回归设计的路径是：合法地址、别名、namespace 和 ManagedAppRole 配置，非空客户端证书/私钥，`ServerName="bad\n"`。该路径先生成自有副本，再在配置校验中失败。本轮没有执行这一路径的运行复现；结论来自控制流与所有权的静态核对。

**影响。** 错误返回后，SDK 新建的秘密副本没有显式尽早清除，只能等待后续内存回收。这是敏感数据生命周期加固问题，不是已发生凭据外泄的证据。

**建议与验收。** 明确新副本的所有权转移点，在失败返回统一清理 SDK 自有副本。定向测试应同时证明失败路径执行清理、成功路径仍可使用、调用方原始配置未被擦除。避免复制多套清理代码，也不要为验证收集真实秘密的堆转储。

### Provider 快照需要先明确兼容的所有权契约

**待决定的契约。** [TokenSnapshot / SecretIDSnapshot](../auth/config.go#L23)没有规定 provider 返回的敏感值由谁持有、谁负责 `Zero`。[sensitive.Bytes](../sensitive/bytes.go#L17)的值复制共享擦除句柄，因此直接清除任意 provider 返回值可能破坏第三方 provider 仍需使用的凭据。

内建 provider 当前每次创建新的快照；[token 管理](../internal/authn/manager.go#L110)和[AppRole 登录](../internal/authn/approle.go#L24)会清除 `RevealCopy` 得到的临时明文，但没有显式清除原快照。这说明所有权和清理责任不够明确，不能在未决定契约前简单补一个通用 `defer Zero()`。

**建议与验收。** 先记录当前调用双方的 observed 行为，提出兼容方案，明确返回值能否共享、SDK 能否取得所有权及调用方责任。覆盖内建独立快照、自定义共享句柄 provider、错误/取消/并发场景，再按确认后的契约实现。Go 运行时与 TLS 已解析私钥的存留边界也应准确记录；不承诺可证明的“所有秘密立即从内存彻底擦除”。

## 可复现性、文档与接入体验

### 远端测试把一次运行的身份固化进源码

**事实。** [Python 远端入口](../scripts/remote-test.py#L52)、[Go 远端配置](../tests/remote/config.go#L102)及相应测试包含固定的运行标识和资源前缀。新的完整运行需要改动多处源码，继而改变源码标识。最新 fixture 的准备与清理逻辑位于被 Git 忽略的 `.artifacts/runs/remote-full-fixture-20260930-08/fixture.py`，并依赖历史报告校验链；仅检出仓库不足以重现完整流程。

**建议。** 提取经过脱敏审查、可复用的 fixture 代码纳入版本管理；将每次运行的目标、namespace、run ID、资源前缀、路径所有权、预算、有效期和清理权限放入校验严格的运行清单。清单不包含凭据，其不可变摘要应进入证据。保留目标 allowlist、请求计数、失败停止和仅清理本次自有资源等保护。

**验收。** 本地测试覆盖非法范围、重复或过期运行、预算不足、资源已存在、越界清理和清理失败；校验失败发生在网络请求前。不能把本次整理理解为新的远端执行授权；之前的 120 请求和时间窗口不自动延续。

### 当前状态散落在多份文档，已经发生漂移

**事实。** [README 开头](../README.md#L7)和[兼容性说明](compatibility.md#L9)仍表示结构调整后没有当前远端成功证据，而最新索引与 handoff 已记录同一源码标识下的补充远端 PASS。README 中明确标记的历史 R1 记录应按历史阅读，不应当作当前结论删除。

[task-status.json](../task-status.json)与[acceptance-results.json](../acceptance-results.json)已较长，多轮历史、当前结论和多个 Markdown 摘要需要手工同步，容易造成“测试已过、页面仍旧”或相反的误导。

**建议。** 保留既有台账与证据来源，建立可校验或可生成的当前状态摘要，并让 README、兼容性与 handoff 引用一致的当前结论。先减少重复维护；如需归档历史，应单独设计保留、链接和读取兼容性，不能删除失败记录或另造平行任务台账。

**验收。** 同一源码标识下，文档对 PASS/BLOCKED/FAIL 的描述一致；历史和当前结果有清晰边界；哈希失配或证据缺失时不能继续显示通过。

### GoDoc 与可执行示例还可完善

**事实。** 项目已有包注释、完整的 Markdown 使用指南和多个示例；不足不是“没有文档”。但公开构造/生命周期方法、部分 DTO 字段的逐符号注释较少，非 `.artifacts` Go 源码中没有 `func Example...`。现有[示例目录](../examples/README.md)覆盖 bootstrap、KV 版本、PKI 签发与保存、Transit 签名等，Encrypt/Decrypt/Rewrap/HMAC、SignCSR/Read/Revoke 的可运行接入示例仍可按需求补齐。

**建议。** 优先为高频路径提供少量可执行、无远端副作用的 `Example`，说明 `New/Start/Close` 生命周期、敏感值所有权、权限要求、错误处理与写入结果不确定时的处理。远端示例保持显式配置与显式执行，不作为默认测试自动访问服务。[Go 官方示例说明](https://go.dev/blog/examples)介绍了示例与包文档、测试的衔接。

**验收。** 示例可编译、确定性运行、不含真实凭据；公开文档与实际方法签名一致；不为凑覆盖率给每个字段机械添加同义注释。

### 发布材料和维护渠道需要具体化

**事实。** [CHANGELOG](../CHANGELOG.md)的未发布区尚未汇总当前大量运行时、工具和测试变化；[SECURITY](../SECURITY.md)缺少可实际使用的私密安全报告渠道，扫描状态说明也应与当前阻塞原因保持一致。

**建议。** 在发布前整理实际变更、兼容影响、未验证项和恢复限制，形成可审阅的发布材料。安全联系方式与支持周期由维护者明确，不编造邮箱或承诺。本评估不授权提交、标签、推送或发布。

## 可延后与不建议扩大范围的事项

- **性能与长稳测试：** 已有性能和 observer 基础，先依据实际并发、轮换频率、延迟目标确定是否增加趋势、饱和与长时间运行测试。没有负载数据时不制定虚构阈值，也不默认引入异步队列或新监控依赖。
- **功能扩展：** 新增 OpenBao 管理接口、更多认证方式或业务工作流应另行确认需求与权限边界；缺少这些能力不自动构成当前 SDK 的缺陷。
- **架构改造：** 不建议再整体搬迁目录、创建通用 `utils/service/repository` 层，或为所有类型增加接口和 builder。现有公开导入路径与兼容性价值更高。
- **依赖升级：** 本评估没有核验“最新版本”，不提出无依据的升级清单。先完成安全扫描，再根据真实风险、兼容性和维护需求决定。

建议先推进已有授权内的构造失败清理、文档一致性、可复用测试代码与最低版本验证设计；正式集成和扫描环境可同时准备。Provider 清理依赖所有权契约决定。某项环境受阻时，应继续独立可做的改进，保留阻塞，不把门禁改成通过。

本轮交付核对：工作区只新增上述两份评估文档，原有 tracked diff 未变、暂存区仍为空；源码摘要未变，文档中的本地链接均存在。`rtk proxy git diff --check` 退出码为 0。没有修改业务代码或重跑测试套件。
