## 三、依次实施

### 1. 使基础工具与验收模块形成单向依赖

重点检查 `scripts/tooling.py`、`scripts/evidence.py`、`scripts/verify-release.py` 及其所有调用方。

- 取消 `tooling.release_problems` 向 evidence 的内部转发，让发布 CLI 直接调用验收模块并显式传入 root。
- 修改全部实际调用方和相关测试后，再删除旧转发入口；不要遗漏函数内动态导入。
- 如有必要，将源码标识、覆盖率等基础能力提取为少量职责明确的叶子模块。不要按函数逐个建文件。
- 基础模块不得反向依赖发布判定或 CLI；导入基础模块不得执行检查、启动进程或退出程序。
- helper 文件移动不得改变仓库 ROOT 定位、工作目录解释、临时 root 注入和跨平台路径语义。
- 严格保持 source_identity v2 的前缀、文件选择、POSIX 排序和原始字节算法，不混同依赖包指纹或上游文件校验和。

结束条件：不存在上述双向依赖，全部调用点已调整；指纹、覆盖率、临时 root 和验收工具回归通过，CLI 调用方式保持兼容。

### 2. 拆分证据校验职责，保留独立门禁判断

重点检查 `scripts/evidence.py` 的 `report_results`、收据/日志辅助函数和 `release_problems`。

- 先在同模块中提取公共基线/收据校验及七类证据的私有校验函数，保留统一入口和返回含义；确有复用需要时再拆文件。
- 将 OB/AC 汇总与日志解析、类别判断分开，依赖关系保持单向。
- 保留 normal、integration、consumer、security、fuzz、tooling、static 各自的要求，不把它们简化成统一“状态为 PASS”的判断。
- 保留自然退出、真实执行目标、非零执行、日志 hash、路径边界、Go 版本、前后标识、基线变化锁存、静态复核限制，以及缺字段/缺报告/未知类别拒绝行为。
- 验证器依据已批准的预期命令和目标检查实际收据；不得直接把生产者返回的命令列表当成充分验收标准，导致生产者和验证器一起改错仍通过。
- 共用数据结构只使用现有依赖或标准库能力，保持负向测试独立。

结束条件：各类别正反例及原门禁回归通过。缺少正式证据时 `verify-release` 仍正确拒绝；门禁退出码变成 0 不是重构成功标准。

### 3. 提取独立的证据测试夹具

重点检查 `scripts/tests/test_release_provenance.py` 和 `scripts/tests/test_ci_summary.py`。

- 将报告、收据、Go 事件和样例文件构造提取为普通 fixture builder，显式接收临时目录。
- CI summary 测试不得再实例化另一个 TestCase 并手动调用其 `setUp()` / `doCleanups()`。
- 各测试管理自己的临时资源和 patch 生命周期，不通过共享 `mock.patch.stopall` 清理其他测试的状态。
- 合成 fixture 保持明确标识且仅用于测试，不能流入真实运行证据或台账验收。

结束条件：两组测试分别运行和组合运行均通过，夹具不依赖测试方法名称、执行顺序或外部全局 ROOT 修改。

### 4. 分离运行记录、Go 探测和 CLI 退出

重点检查 `scripts/reporting.py`、`scripts/record.py`、`scripts/command_runner.py` 及各 runner。

- 保留现有公共命令执行器，提取不依赖 Go 的小型运行记录能力，共用必要的初始化、命令收据及持久化逻辑。
- `go version` 由 Go runner 显式执行，构造通用记录对象不应隐式探测 Go 或结束整个进程。
- 可复用层返回结果或抛出明确异常，CLI 负责退出码转换；必须继续确保清理不完整时立即停止，不执行后续检查。
- 保留自然退出、超时、工具缺失和中断的区别，以及仅回收本次创建进程的边界。
- 保留不可变 run_id 证据、已有路径/文件名约定、禁止覆盖、latest 指针更新语义及前后源标识检查，不为合并实现而降低要求。
- 保持各 CLI 参数、Makefile/CI 调用及报告消费者兼容。Python tooling 检查本身不得依赖可用的 Go。

结束条件：工具缺失、探测失败、超时、中断、清理不完整、重复 run_id 和基线变化回归通过，各受影响 runner 的实际可执行检查完成。

### 5. 按需整理配置校验

如果本轮实际触及 `config.go`，且局部提取有明确收益，在同一 `bao` 包内将 `normalizeConfig` 按地址、认证、TLS、预算/限额提取少量私有函数。

保持现有校验先后、默认值、输入拷贝、错误码及 operation 标签，保持 `New` 不联网；不引入新包、新公开接口或通用校验框架。验证正常值、整数溢出、TLS 空文件、namespace 等边界。没有必要时明确暂缓，不为“完成六项”制造改动。

### 6. 按需整理测试归属

新增或实际触及 `review_fixes_test.go`、`hardening_test.go` 中的测试时，局部归入 lifecycle、TLS、KV、PKI、Transit 或执行语义对应文件。

## 四、验证与证据纪律

先从实际脚本、Makefile、CI 和工具版本确认命令、副作用与前置条件，再执行。遵守 RTK 和 PowerShell UTF-8 规则，每次运行一项可观察操作；超过 30 秒给出简短进度。

RTK 用于外层 shell 调用；报告仍应记录实际被检验进程的 argv、工作目录和自然退出码，不把包装器退出成功当成测试成功。

1. 重构前取得相关工具测试和 Go 聚焦测试的现状证据。已有失败单独记录，不用旧报告假定当前通过；若发现真实 Bug，先取得失败用例或可复现证据再修复。
2. 每个执行单元完成后运行受影响的聚焦回归；测试修改由主代理完成，不降低断言、阈值或验收规则。
3. 工具测试全集入口为 `rtk proxy python -B -m unittest discover -s scripts/tests -v`。两组共享夹具测试还须分别执行，确认没有顺序依赖。
4. 完成代码、测试及门禁输入调整后冻结新的 source_identity，再重建必要的真实运行证据。脚本变化同样会改变指纹，不能只重跑 Python 测试却把旧 Go 报告标成当前 PASS。
5. 在现有环境可执行的范围内，使用项目正式入口重新执行 normal-test、五目标 fuzz、独立消费者、benchmark 及受影响示例检查。normal-test 的 coverage 必须来自本轮自然成功的 race，全部 15 组仍至少 85% Go 语句覆盖率；失败时不得读取旧 profile。
6. 保留正式工厂验证、五个 fuzz 目标各自的非零执行证据、四个 benchmark 及启用子基准三轮有效样本。benchmark 不新增发布硬门槛，不从均值推导分位数或编造性能改善。
7. 真实集成、固定扫描器、Linux/最低 Go 版本和远端 CI 等检查仅在其输入、环境及授权实际满足时执行。既有外部阻塞继续如实保留，不安装工具、猜测版本/digest、使用 latest 或触发远端运行来消除红灯。
8. 使用现有命令执行器和不可变证据目录记录工作目录、平台/工具、前后标识、真实命令、执行目标、自然退出码及脱敏日志位置。保留首次失败、超时和重跑，区分 PASS、FAIL、BLOCKED、NOT_RUN；零测试、skip、缺目标不能算通过。
9. 执行 `rtk proxy python -B scripts/verify-release.py`，逐项说明当前拒绝原因。旧证据失配是应当重建的证据缺口；外部输入缺失是交付阻塞，两者不得混淆。

不使用 overlay、replace、跳过 vet、删除失败测试、放宽规则、手改报告 hash 或合成日志取得通过。若冻结后再次修改纳入指纹的文件，重新确定基线并重建必要证据。

## 五、独立审查、收尾和交付

对稳定差异安排独立 risk_reviewer，重点检查门禁是否放宽、验收是否失去独立性、路径是否越界、报告是否被覆盖、异常/退出是否漏掉进程回收，以及配置或测试迁移是否改变公开语义。审查者只读；主代理核实并修复成立的问题，再执行受影响验证。审查本身不能替代实际测试。

更新现有交接入口、必要接入/测试文档和原 OB/AC 的证据关联。保留历史记录，不另建第二套台账，不因结构重构完成就把存在依赖阻塞的任务改为 VERIFIED。

收尾检查工作树、暂存区、相关未跟踪文件、最终指纹、报告归属和本次创建的进程/临时资源。保护用户原有修改，不自行清理无法确认归属的资源。

仅当关键缺失信息会改变正确性、授权或交付条件时集中列出所需输入，等待期间继续独立任务。命令无响应时先核对真实进程，再缩小范围或更换可验证路径，不反复盲等。不得在步骤结束或审查结束时自行停止仍可执行的工作。
