## 一、目标与执行范围

**Goal**：验证并修复 Transit 编码后请求体检查过晚的问题，保持既有安全与契约边界；形成对应当前源码的验证证据、稳定候选交付基线和业务接入交接材料。

**Scope**：

- 当前仓库中的 Transit 相关实现、必要的回归测试和相关文档。
- 当前源码、工作树差异及现有发布证据的核对；执行前置条件已经满足的本地检查。
- 实际模块交付的候选范围与验真步骤。
- OB-019 / AC-072 的业务接入准备，以及精确数字字段的消费者契约建议。

**Out of scope**：

- 无关重构、替换框架、扩大 SDK 功能、全仓格式化、擅自升级依赖或调整最低 Go 版本。
- 未明确授权的暂存、提交、推送、分支或标签操作、发布、部署及生产数据操作。
- 未明确授权的依赖安装、共享服务启停、迁移、真实远端写入或扫描。
- 未提供实际业务仓库及明确接入范围时，实现或宣称完成真实业务迁移。

**Likely changes**：根据复现结果，定点修改 `transit_client.go`、`transit_cipher.go`、`transit_hmac.go` 中确实存在相同问题的路径、对应测试，以及必要的契约/测试/交接文档。只有现有结构确实需要时才增加一个小型内部共用帮助函数，不为统一外观重写整个 Transit 层。

**Risks**：参数校验与网络预检顺序变化可能影响错误优先级；提前编码必须维持敏感缓冲区清理和资源上限；源码变化会使旧报告的源码标识过期；本地代理消费者通过不等于目标仓库可获取；SDK 门禁通过不等于业务接入通过。

**Validation**：先证明具体边界行为，再运行针对性回归和受影响检查；发布相关判断使用现有脚本、规则和实际证据，不改弱标准。

**Stopping condition**：可执行的本地实现、相关回归、必要文档和交付准备完成；未能执行的必需检查及业务接入依赖有明确的最小阻塞、解除条件和交接信息。仍缺必需验证时只能报告“实现完成，验证未完成”，不能把整个工程验收标为通过。

## 三、先建立稳定候选基线，再实施 Transit 优化

### 3.1 固化审查边界

记录本轮开始时的源码标识和候选改动范围。这里的“固化”是明确内容、标识和证据，不自动执行 Git 暂存或提交。区分用户已有改动与本轮新改动；最终候选文件和片段清单必须能够追溯到该基线。

### 3.2 验证建议在当前实现中是否成立

检查报告指出：`transit_client.go` 的签名路径先比较原始消息长度，再读取公钥元数据，最后才进行 Base64/JSON 编码；`internal/engine/client.go` 在执行阶段限制最终请求体。

确定的边界示例：默认上限 1,048,576 字节，800,000 字节消息的 Base64 长度为 1,066,668 字节，还不包括 JSON 开销。因此原始消息可能通过初步检查，而最终编码请求体必然超限。

先用项目既有 fake sender、请求计数和测试模式复现，不访问真实 OpenBao。明确是否发生额外元数据请求、是否可能被元数据读取错误遮蔽，以及当前最终大小门禁是否有效。它是低优先级的本地预检优化，不预设为越限写入或高风险漏洞。

如果当前实现已解决该问题，以当前证据说明该项不再需要修改；继续完成其余独立任务，不为制造改动而重构。

### 3.3 最小修复与契约约束

对确认存在问题的路径，在任何元数据请求或认证快照获取之前，尽可能完成最终 JSON/Base64 请求体的大小判定；采用实际编码长度或等价可靠的计算，不能只比较原始输入长度。

逐项核对 Sign、Verify、Encrypt、Decrypt、Rewrap、HMAC、HMACVerify 等相关路径，只修改问题成立的位置。必须保持：

- `MaxRequestBytes` 对最终请求体字节数的约束，边界与执行器一致；超限返回 `invalid_argument`，`Effect` 为 `none`。
- 操作级超时、取消、客户端生命周期、认证准入和并发槽规则。
- 密钥类型、版本、退休版本、派生上下文和算法兼容性预检；不引入公钥缓存，不猜测服务器能力。
- 签名响应的本地验证、规范 Base64、版本匹配及畸形响应拒绝。
- 敏感数据所有权、显式副本与清理；正常和失败分支都处理新建缓冲区。
- 写操作不自动重放，以及错误码、重试和 `UNKNOWN` 语义。

在实现前明确需要改变的本地错误优先级，核对既有契约和调用方，必要时同步最小文档说明。其他参数、状态或权限语义发生冲突时，不擅自重新定义合同。

### 3.4 回归测试

至少覆盖：

1. 原始输入未超限、Base64/JSON 编码后超限：返回本地参数错误，元数据和业务请求计数均为零。
2. 编码后恰好等于上限时可进入既有正常流程；超过一字节时拒绝。
3. 元数据 sender 配置为失败，超限输入仍在本地拒绝，验证错误没有被网络预检遮蔽。
4. 普通合法输入仍保持元数据预检、正确的版本/算法和最终请求内容。
5. 本次改变影响的取消、错误优先级及敏感值所有权/清理场景。

测试验证外部行为和请求边界，不机械复制实现。优先使用较小配置上限构造清晰、快速的用例；仅在必要时使用完整的默认大小示例。

## 四、业务接入准备与精确数字约定

OB-019“既有项目接入与回滚演练”当前属于 `OUT_OF_SCOPE`，AC-072 是实际业务接入发布条件。SDK V1 门禁要求 AC-001～071。不能把它们混为同一验收，也不能为了显示全部完成而改写范围或台账。

没有实际业务仓库、明确授权和非生产接入环境时，只完成可审阅的交接准备并保留该任务原有范围。利用 `examples/credentialworkflow/workflow.go` 和既有集成指南列明：

- 业务侧 Issuer、Store、Journal 的实现责任和持久化边界。
- 原子领取/并发竞争、操作 ID 与资源 generation、发证后中断、保存结果未知及核对策略。
- 重启不重复发证、凭据轮转、历史引用保持和回滚演练的验收场景。
- 缺失的仓库/模块、环境、测试资源和授权，以及解除阻塞的最小输入。

若会话中已经提供实际业务仓库和明确接入授权，则核对该仓库的当前基线、合同和独立环境，按上述场景继续执行；不得仅凭示例接口存在就宣称业务接入完成。

`docs/compatibility.md` 已说明服务端大整数精度边界。要求精确的业务 ID/大整数应由消费者契约规定为 JSON 字符串，并加入实际接入验收。它是契约建议，不授权 SDK 自动将现有数值字段转换成字符串。不得把本地 `kv.Document` 往返通过解释为服务端端到端精度保证。

## 五、验证与证据更新

先从当前 Makefile、CI、测试文档和脚本确认准确入口、所需工具链及副作用，再执行检查。使用已有授权的非生产资源；缺少依赖、工具链或 fixture 时，记录最小阻塞并继续独立工作，不擅自安装、联网或启停共享服务。

1. 先执行新增边界用例及受影响的 Transit、执行器和所有权回归，再按改动影响运行根模块单元测试、vet 和适用的 race 检查。
2. 工具脚本没有修改时，不无依据反复运行全量工具测试；如果修改了证据或报告工具，则运行对应 Python 回归。
3. 正式报告使用项目要求的固定工具链、平台和现有入口。本报告的 Go 1.26.3 离线检查不替代 Go 1.26.8 正式报告，也不替代最低 Go 1.25.0 兼容性证据。
4. 源码标识变化后，按 `scripts/acceptance-rules.json` 和现有验证器判定失效范围。需要新的 NORMAL、REAL_OPENBAO、独立消费者、安全扫描或最低版本报告时，用实际执行生成；不能只替换旧报告 hash、复制 PASS 或放宽规则。
5. 保存真实 argv/cwd、源码前后标识、工具链、平台、自然退出码、测试筛选及计数、首次失败/重跑记录和脱敏证据位置。命令返回 0 仍需确认目标确实执行；父/子测试事件不能冒充独立验收数量。
6. `verifier` 只允许写明确授权的缓存、构建产物、日志和测试资源。需要修改源码、测试、台账或生成项目文档时由主代理处理；先确认包装脚本没有越界写入。
7. 使用现有 `current-status.py --check` 和 `verify-release.py` 等入口复核最终状态。更新必要状态文档时由主代理运行现有生成流程，不手工伪造门禁结果。

验证项分别报告 PASS / FAIL / BLOCKED / NOT_RUN。静态阅读、当前有效的既有报告校验和本轮新执行的检查分别说明。缺少必需证据时不能宣称发布门禁通过，更不能宣称已经发布。

命令遵循有效 RTK 和 UTF-8 规则。一次运行一个清晰操作；超过 30 秒报告当前操作和最新已确认结果。遇到不响应或超时，核对进程与产物后缩小范围或换原生执行路径，并报告替代方法及结果，不持续重复等待。

1. 结果：已完成、未完成及暂缓项，区分 SDK 完善和真实业务接入。
